# Architecture

dicomqc finds files, reads their metadata, runs checks, and writes reports.
Each step has its own module. The checks and report writers use dicomqc's data
models rather than pydicom objects.

## Components

| Component | Current responsibility |
| --- | --- |
| CLI and scanner | Find input files recursively, select a profile, and request reports. |
| `DicomBackend` | Read one file and return its metadata as a `MetadataRecord`. |
| `PydicomBackend` | Parse DICOM metadata with `stop_before_pixels=True`; pixel data is not loaded. |
| Metadata model | Store file details, tags, private-tag status, and `ValueState`. |
| Built-in rules | Evaluate direct PHI fields, pseudonym patterns, and private tags under `research-release-v0.1`. |
| Result model | Collect records, findings, skipped files, counts, and the process exit status. |
| Report writers | Write JSON, CSV, and MultiQC-compatible reports without raw tag values. |

## Data flow

1. `scan_paths()` collects input files in a repeatable order.
2. The backend reads each file as DICOM metadata. Files that cannot be parsed are
   recorded as skipped rather than silently ignored.
3. pydicom elements are converted to `DicomTag` objects inside a
   `MetadataRecord`.
4. Built-in rules inspect metadata and create `Finding` objects with severity,
   tag details, and recommended fixes.
5. `ScanResult` combines records, findings, and skipped-file reasons. Its exit
   code is `0` for pass, `1` for review warnings, and `2` for errors or skipped
   files.
6. Report writers save the results without raw DICOM tag values.

## Reading metadata

Metadata readers implement this protocol:

```python
class DicomBackend(Protocol):
    def read_metadata(self, path: Path) -> MetadataRecord:
        ...
```

The scanner and rules use `MetadataRecord` objects. Another reader could return
the same objects without requiring changes to the rules.

## What stays out of reports

`MetadataRecord` stores modality, manufacturer, Study Instance UID,
Series Instance UID, and tags. Each `DicomTag` stores its number, keyword, value representation,
private-tag status, value state, and an internal raw value.

Rules need raw tag values for checks such as pseudonym matching. Report writers
omit those values. Reports still contain file paths and other context that may
identify people or datasets, so review them before sharing and restrict access
when needed.

## Planned extensions

The current package has one built-in profile. Future plugins, configurable
policies, vendor metadata summaries, and standards-specific checks would use
the same reader and rule interfaces. See [Planned Features](./extending-dicomqc.md).
